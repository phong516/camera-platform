RTSP Playback in Qt Quick

The URL enters a player; decoded frames enter the scene.

Preferred first experiment

RTSP URL → Qt MediaPlayer → VideoOutput → QML scene graph

MediaPlayer owns playback and decoding through the selected Qt Multimedia backend. VideoOutput receives the video output and paints it as a Quick item. QML owns layout; it does not need to manipulate GStreamer objects.

import QtQuick
import QtMultimedia

Item {
    MediaPlayer {
        id: player
        source: "rtsp://127.0.0.1:8554/hd"
        videoOutput: output
        onErrorOccurred: (error, errorString) => console.error(errorString)
    }

    VideoOutput {
        id: output
        anchors.fill: parent
        fillMode: VideoOutput.PreserveAspectFit
    }

    Component.onCompleted: player.play()
    Component.onDestruction: player.stop()
}

Build and verify

  • Add Qt Multimedia to the Qt components found by CMake and link Qt6::Multimedia to the client target.
  • Use an RTSP URL that is reachable from the client. The architecture's planned local profile URL is rtsp://127.0.0.1:8554/hd; the profile server is not implemented yet.
  • Check errorString, hasVideo, and playbackState on the actual Qt/backend/codec combination. A live stream may report duration == 0; that alone is not a failure.
  • Run the visual test on a machine/session with a working display. A headless server test cannot prove that QML rendered frames.

When to choose the other path

Use GStreamer's qml6glsink only when direct pipeline control is worth adding GStreamer to the client. It inserts a Quick item into the scene graph and has OpenGL display/context ordering requirements. A custom appsink-fed QQuickItem is a lower-level fallback: the app must safely move frames from the streaming thread to Qt's render thread.

Primary sources: Qt MediaPlayer, Qt VideoOutput, Qt Multimedia overview, and GStreamer qml6glsink.
