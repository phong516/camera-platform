Polling, Twice

A polling client asks the server again. A polling server asks the kernel which sockets are ready. Same word, different jobs — and only the second one is about poll(2).

Mission tie-in: the Qt client refreshes the control plane every 500 ms (CameraBackend), and WebServer is the process that answers those refreshes. This lesson builds the smallest C server that can answer many polling clients from one thread, then maps it onto the WebServer contract already in the repo.

Two different polls

Polling styleWho initiatesWhat it costs
Client pollingThe UI asks GET /api/status every 500 ms.Simple, stateless, easy to retry. The server sees a fresh connection each time.
Server poll(2)The server asks the kernel which file descriptors are readable.One thread can wait on the listen socket and every client socket at once. No thread per connection.

The two compose naturally: many clients poll the server, and the server uses poll() to serve all of them without blocking on the slowest one.

Why blocking accept() is not enough

The current WebServer contract is deliberately serial: accept one connection, read one request, reply, close. That is enough for one client at a time and easy to reason about. It stops being enough when a client connects and then sends nothing — a blocking read() parks the only worker until the receive timeout expires.

blocking loop                       poll() loop
accept() ── one client              poll() ── many fds
read()   ── wait for that client    ready? ── service only those
write()  ── reply                   repeat
close()  ── next client             slow client costs one slot

poll() does not read for you. It only tells you which descriptors are ready now. The loop still owns the read, the buffer, the parse, and the close.

What the measurements show

1. A silent client does not stall the others

# hold one connection open for 2 s without sending a byte
( exec 3<>/dev/tcp/127.0.0.1/18080; sleep 2 ) &

# meanwhile, five normal requests
for i in 1 2 3 4 5; do
  curl -sS -o /dev/null -w '%{time_total}\n' \
    http://127.0.0.1:18080/api/status
done
0.000363
0.000360
0.000402
0.000632
0.000369

Sub-millisecond responses while another socket sits idle. The status body also reported "activeClients":2: the idle client occupies a slot, not the server.

2. 500 requests, 50 at a time, one thread

seq 1 500 | xargs -P 50 -I{} curl -sS -o /dev/null \
  -w '%{http_code}\n' http://127.0.0.1:18080/api/status \
  | sort | uniq -c
    500 200
500 requests, 50 parallel: 1247 ms

All 500 succeeded. The 1247 ms includes starting 500 curl processes — this is a correctness probe, not a throughput benchmark. The server's single thread stayed inside poll() and serviced whichever sockets were ready.

3. A request can arrive in pieces

( printf 'GET /api/status HT'; sleep 1; \
  printf 'TP/1.1\r\nHost: x\r\n\r\n'; sleep 0.2 ) \
  | nc 127.0.0.1 18080 | tail -1
{"status":"ok","requests":509,"uptimeSeconds":15,"activeClients":1}

The first recv() returned only GET /api/status HT. The lab kept the partial bytes in that client's buffer, went back to poll(), and finished the request when the rest arrived one second later.

4. Shutdown is a flag, not a thread cancel

[serve] stopped: 509 requests

Ctrl-C sets g_stop; poll() returns on the signal, the loop exits, then the listen socket and every client are closed. The 1 s timeout is also the place to put periodic housekeeping later.

The loop in seven steps

StepCodeWhy
1. Build the fd setpfds[0] = listen_fd; append every live clientOne array is the whole wait set.
2. Waitpoll(pfds, nfds, 1000)Sleeps until data, a new connection, a signal, or the timeout.
3. Drain acceptsaccept() until EAGAINThe listen fd is non-blocking; one wakeup may mean several pending connections.
4. Service ready clientsrecv() only on POLLINReadiness comes from the kernel, not a guess.
5. Buffer the bytesappend to client.bufOne recv() is not one request.
6. Parse and replyfind \r\n\r\n, then 200/404/405Same job parseRequest() and dispatch() do in WebServer.
7. Closeclose(fd), free the slotOne request per connection is the contract; no keep-alive state to track.

Traps this lab keeps visible

Readiness is not completeness

POLLIN means "at least one byte is available", not "the whole request arrived". The buffer and the \r\n\r\n search are mandatory.

A non-blocking listen fd, but not a magic non-blocking server

The lab sets only the listen socket to O_NONBLOCK so the accept drain can stop at EAGAIN. Accepted sockets stay blocking because the response is tiny and poll() already told us a read will not block. A production server that can write large bodies must handle partial writes too.

A slow client costs a slot

MAX_CLIENTS is 64. Measured: 64 connections held open, then the 65th request returned 503 and logged [busy] ... rejected. That is a deliberate bound, not an accident. Without it, the array is the new unbounded resource.

One thread is still one thread

poll() removes waiting, not work. A handler that blocks on disk, GStreamer, or a mutex stalls every client. The control plane should hand long jobs to the application and return a state snapshot, not perform the job inside the HTTP handler.

Your repo step

Implement WebServer::run() to the contract already written in web/WebServer.hpp: blocking accept(), one request per connection, 8 KiB cap, 5 s SO_RCVTIMEO, parseRequest(), dispatch(), serializeResponse(). That is the serial version — and it is the right first version.

Then test it with two overlapping clients:

# terminal 1: a client that connects and sends nothing for 6 s
( exec 3<>/dev/tcp/127.0.0.1/8080; sleep 6 ) &

# terminal 2: a normal request; time it
curl -sS -o /dev/null -w '%{time_total}\n' \
  http://127.0.0.1:8080/api/status

With the serial contract, the second request waits for the first connection's 5 s receive timeout. That is the measured cost of the simple design. If the control plane needs to tolerate that, replace the accept/read body with this lab's poll() loop; the parser, dispatcher, and serializer do not change.

Retrieval check

What does poll() guarantee when it returns?

poll() reports readiness. The request may still be partial; the caller reads and buffers.

Why does the lab keep a per-client buffer?

TCP is a byte stream, not a message stream. The \r\n\r\n search finds the boundary; the buffer preserves what has arrived so far.
