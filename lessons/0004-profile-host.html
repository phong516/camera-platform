ProfileHost: Two Profiles, Zero Drama

One source, N profile bins on a tee, switches flipped while running — the full Phase 2 topology in C++.

Mission tie-in: This is the shape of server/ProfileHost: a host that owns the source chain and the tee, attaches one ProfileBin per profile, and exposes setProfileDrop(name, bool) — which the CLI --drop flag will call, and later the web API too.
Answering Lesson 2’s parked question

Lesson 2 ended with: “when a profile is dropped mid-run, what should its consumer see?” The mechanism part is now measured — the branch goes silent (frozen last frame once RTSP is involved), and the rest of the pipeline doesn’t notice. The UX decision (freeze vs. signal) stays parked until the RTSP lesson, but you can now reason from facts instead of guesses.

Concept: profiles are data, not code

With ProfileBin as a box (Lesson 3), the host is a loop, not a pipeline diagram:

videotestsrc(is-live) ! videoconvert ! caps(I420,1280x720@30) ! tee ─┬─▶ bin "hd"  (720p@2500k)
                                                                      └─▶ bin "sd"  (480p@1200k)

Each profile is a config row — name, size, bitrate, output — and the host does per row: build bin, add to pipeline, request a tee src pad, link it to the bin’s ghost pad. A third profile is a third row, not a third copy of the code.

Control stays the same as the lab: gst_bin_get_by_name(bin, "pvalve") → set drop. One subtlety explains why dropping sd never disturbs hd — and it is the same reason the queue comes first inside the bin:

Why the tee never stalls

The queue is the element closest to the tee, so all encoder work runs on the queue’s private thread. When valve.drop=true, that thread keeps pulling buffers out of the queue and discarding them into the valve at full speed. The queue never fills, so the tee’s push into this branch never blocks, so no other branch is throttled. Dropping costs (almost) nothing and damages nothing.

What the resume tells you about the queue

If the queue had buffered ~1 s of frames while dropped, re-opening the valve would spray them all at once (a timestamp jump for any consumer). It didn’t: dropped buffers pass through the queue and die in the valve immediately, so the slack stays available and the branch resumes with perfect timing. Queue-first placement inside the bin buys you this — remember it when you place your review of ProfileBin.

Check yourself

1. Inside ProfileBin, why is the queue closest to the tee?

The queue is the thread boundary: everything downstream of it — valve, scale, encode, sink — runs on the queue’s private src thread. The tee’s push just fills a buffer and returns.

2. What happened to sd’s output file during the drop window?

481,104 B at t=3, t=5, t=6 — drop-all discards every buffer after the valve, with zero leakage. That determinism is what makes drop a safe runtime operation.

3. What does a mid-run drop mean for that profile’s consumer?

The default drop-mode=drop-all swallows buffers and events: downstream just waits. No gaps, no EOS. Whether we want to change that for RTSP clients is the parked UX question from Lesson 2.
