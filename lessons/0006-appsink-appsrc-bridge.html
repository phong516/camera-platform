The appsrc Bridge: Viewers Drive the Valves

Your ProfileHost produces H.264 into an appsink. The RTSP factory wants an appsrc. Ten lines of glue connect them — and two traps cost us a full debugging session so they don't cost you one.

Mission tie-in: This is server/RtspProfileServer, completely designed: factories whose launch is just appsrc ! h264parse ! rtph264pay, wired to your ProfileHost appsinks on media-configure, unwired on unprepared. Viewer arrival opens the profile's valve; the last viewer leaving closes it. Your Phase 2 architecture, running.

Concept: two islands, one bridge

ProfileHost island                                RTSP island (per media session)
                                                   ( appsrc name=vsrc ! h264parse ! rtph264pay name=pay0 )
x264enc ─▶ appsink ════ bridge ════▶ appsrc
            ("new-sample" pulls a sample)  (push, session re-stamped)

The two islands know nothing about each other. The glue is event-driven:

EventWho hears itWhat the bridge does
A viewer requests the mountfactory media-configuregrab the new media's vsrc, store it, open the valve
Every encoded frameappsink new-samplecopy buffer, strip timestamps, push into the wired appsrc
The last viewer leavesmedia unprepareddrop the appsrc reference, close the valve

Because these three events run on different threads (RTSP main loop vs. each appsink's streaming thread), the pointer hand-off needs a mutex — the same pattern you will copy into RtspProfileServer.

Trap 1 — the valve startup rule, applied

Lesson 2's rule, made concrete: the lab starts with both valves open, waits for gst_element_get_state() to confirm PLAYING, then closes them ("idle") until viewers arrive. Cost: exactly the frames that pass during that window.

[bridge] pipeline PLAYING
[bridge] idle: both valves closed      <- ~2 frames per profile escaped before the drop
[status] hd session=0 pushed=0 dropped=2 valve_drop=yes wired=no

Trap 2 — the timestamp trap (why our first run streamed 0 fps)

First working bridge, first test: server says it pushed 179 frames; every client received zero.

[client] rtsp://127.0.0.1:8554/hd: samples=0 over 6.0s => 0.0 frames/s
[status] hd session=1 pushed=39 ... pushfail=0   <- appsrc accepted everything happily

The cause: we pushed samples carrying the producer's timestamps (the ProfileHost pipeline's running time — its own clock, its own zero). The RTSP media session is a brand-new pipeline; its RTP clock slaving (rtspsrc arrives in buffer-mode=slave) aligns the client to the stream's timeline — and a foreign timestamp baseline never converges. No frames render, no error is raised anywhere.

The relay fix — restamp at the appsrc boundary

In new-sample: copy the buffer, clear PTS/DTS/duration, set the appsrc caps once from the sample's caps, and add do-timestamp=true to the appsrc launch. The media then stamps each frame on arrival — the correct semantics for a live relay: "this frame is happening now", not "this frame was frame #4,382 of another pipeline".

GstBuffer *buffer = gst_buffer_copy(gst_sample_get_buffer(sample));
GST_BUFFER_PTS(buffer) = GST_BUFFER_DTS(buffer) = GST_BUFFER_DURATION(buffer) = GST_CLOCK_TIME_NONE;
/* once per session: */ gst_app_src_set_caps(appsrc, gst_sample_get_caps(sample));
gst_app_src_push_buffer(appsrc, buffer);   /* takes ownership */

Before → after, same lab, same client, only the restamp changed:

before:  hd samples=0     sd samples=0     hd(session 2) samples=0
after:   hd samples=151 / 6.0s = 25.2 fps
         sd samples=137 / 6.0s = 22.8 fps
         hd samples= 91 / 4.0s = 22.8 fps   (session 2, after full teardown + reconnect)

ObservationNumbers
The valve lifecycle is exactly what the architecture wanted. Idle = valve closed, encoder stopped. Viewer = open + stream. Last viewer gone = closed again. The second hd session (full media teardown in between) worked identically.2 sessions, 3 connect cycles
Viewer-join was measured at ~2 s in the instrumented debug run — two ~1 s waits inside gst_rtsp_media_prepare for appsrc-fed live media. Later re-measurement with the final binaries: 31 ms first frame (Lesson 9). The ~2 s did not reproduce; treat it as a red herring of that debug build.+948 ms, +971 ms → later: 31 ms
The join cost shows up as frame loss, not delay. Producer pushed 179 frames during hd's 6 s session; client counted 151 — the ~1 s of frames pushed before the client's pipeline was rendering either overflowed the appsrc queue or arrived as a startup burst.179 pushed vs 151 counted
Idle branches stay cheap. With the valve closed, the drop happens at the valve, before the encoder — the appsink sees nothing, the bridge's drop counter stops moving. Idle cost = queue+valve forwarding only.dropped stays flat when idle
Two facts to carry into RtspProfileServer

1. The ~2 s media-prepare cost came from one instrumented debug run and never reproduced with the final binaries (Lesson 9 re-measured 31 ms first frame). Keep the lesson: measure with the artifacts you will actually ship, and re-measure before you quote a number to anyone.

2. Never push producer timestamps across the bridge. If a future refactor "optimizes away" the buffer copy, this bug comes back — with zero errors and zero frames, which is a terrible debugging experience twice.

Check yourself

1. The bridge pushed with the producer's timestamps. Why did clients render nothing — with no errors anywhere?

The RTP session slaved to the producer pipeline's running time — a clock that never maps to the media session's own timeline. Every push succeeded; nothing ever rendered. Restamp at arrival fixes it.

2. Where must the appsink→appsrc wiring happen so reconnects keep working?

Lesson 5 showed media is destroyed when viewers leave and rebuilt on return (bin2). The bridge must re-wire the fresh vsrc each time — and drop the stale pointer on unprepared.

3. Both viewers leave a profile. What should the bridge do, and what does it cost while idle?

Measured: valve closed on unprepared; frames die at the valve before the encoder, and the media itself was already torn down by the server. Idle profiles cost almost nothing — which is exactly the lazy-profile design the architecture asked for.
