One Source, Two Roads

How tee splits a stream — and why every branch needs its own queue.

Mission tie-in: Phase 2 of camera-platform needs one camera capture to feed an HD profile and an SD profile (and more later). tee is the fork in that road; queue is what keeps the branches from tripping over each other.

Concept: the fork

tee (T-junction) copies each incoming buffer to every src pad it has. Each output pad is a new road:

            ┌─ t. ! queue ! … HD branch
videotestsrc┄!videoconvert┄!capsfilter┄! tee name=t
            └─ t. ! queue ! … SD branch

Two facts about tee determine everything that follows:

  1. Every buffer goes to every branch. Nothing is load-balanced or dropped — the same 1080p frame is handed to the HD road and the SD road.
  2. Pushes happen one branch at a time, in the same thread that delivered the buffer to the tee. The tee cannot move on to branch B until branch A's push has returned.

A queue placed on a branch changes fact 2: its sink side accepts the buffer and returns immediately — the push into the tee never waits. A private thread on the queue's src side then moves buffers onward. That thread boundary is the real gift: producer and consumer can run at different speeds, with the queue acting as a shock absorber between them. The official docs put the rule plainly:

From the docs

“One needs to use separate queue elements (or a multiqueue) in each branch to provide separate threads for each branch. Otherwise a blocked dataflow in one branch would stall the other branches.” — tee documentation

Run the labs below in WSL to see this rule earn its keep. Every lab uses 320×240 I420 frames — 115,200 bytes per frame — so you can count frames by dividing file size.

Lab: watch the rule work

E1 tee + queue on both branches — the happy path
gst-launch-1.0 -q videotestsrc num-buffers=60 ! videoconvert \
  ! video/x-raw,format=I420,width=320,height=240,framerate=30/1 ! tee name=t \
  t. ! queue ! filesink location=a.raw \
  t. ! queue ! filesink location=b.raw
stat -c '%n %s B' a.raw b.raw

Result — both files exist and are identical:

a.raw 6912000 B     # 60 frames × 115,200 B
b.raw 6912000 B     # every frame reached every branch
E2 remove the queues — total deadlock (try it yourself)
timeout 5 gst-launch-1.0 videotestsrc num-buffers=60 ! videoconvert \
  ! video/x-raw,format=I420,width=320,height=240,framerate=30/1 ! tee name=t \
  t. ! filesink location=a.raw \
  t. ! filesink location=b.raw

It never starts. It prints forever:

Setting pipeline to PAUSED ...
Pipeline is PREROLLING ...        # stuck here until timeout kills it

and both files stay at 0 B. Why:

  1. A sink must hold its first buffer and wait before it can render — the pipeline completes preroll only when every sink has received one. (preroll design doc)
  2. The first filesink therefore blocks the tee's push to branch A until the pipeline reaches PLAYING.
  3. PLAYING requires branch B's sink to get its first buffer — but the tee is still stuck on branch A and never gets to branch B.

Circular wait. Adding queue to just the first branch breaks this particular deadlock (the queue's instant return lets the tee reach branch B) — but the second branch still throttles everything, as the next lab shows.

E3 queue on the fast branch only — slow branch drags it down
timeout 4 gst-launch-1.0 -q videotestsrc num-buffers=60 ! videoconvert \
  ! video/x-raw,format=I420,width=320,height=240,framerate=30/1 ! tee name=t \
  t. ! queue ! filesink location=fast.raw \
  t. ! identity sleep-time=500000 ! filesink location=slow.raw
stat -c '%n %s B' fast.raw slow.raw

identity sleep-time=500000 simulates a consumer that needs 0.5 s per frame (~2 fps). After a 4-second window:

fast.raw 921600 B    # 8 frames
slow.raw 806400 B    # 7 frames — fast is stuck at the same pace

Without a queue on the slow branch, its sleeping pushes hold the tee — and the tee holds everyone.

E4 queue on both branches — the fast branch gets ahead
timeout 4 gst-launch-1.0 -q videotestsrc num-buffers=60 ! videoconvert \
  ! video/x-raw,format=I420,width=320,height=240,framerate=30/1 ! tee name=t \
  t. ! queue ! filesink location=fast.raw \
  t. ! queue ! identity sleep-time=500000 ! filesink location=slow.raw
stat -c '%n %s B' fast.raw slow.raw
fast.raw 4492800 B    # 39 frames
slow.raw  806400 B    # 7 frames — fast ran ahead

Fast jumped ~1 second ahead (≈30 frames of slack) before the slowest branch set the pace again. That ~1 s is no accident: a queue's default max-size-time is exactly 1 second (also 200 buffers, 10 MB — whichever limit hits first). Queues buy you bounded independence, not infinite.

Rules to keep
  • Put a queue on every branch after a tee. No exceptions.
  • The queue gives each branch its own thread and a bounded buffer of slack (defaults: 200 buffers / 10 MB / 1 s).
  • Beyond that slack, the slowest branch still sets the overall pace. Tune with max-size-*, or drop old data deliberately with leaky=downstream.

Check yourself

1. A queue on every tee branch gives you…

The queue returns from chain() instantly (so the tee never blocks) and its own thread drains buffers downstream — that is the decoupling.

2. Two filesinks with no queues hang at startup because…

Sinks wait during preroll; the tee pushes sequentially; so branch B never receives the buffer its preroll needs. Circular wait — only a queue breaks it.

3. The default queue limits are…

Any one limit blocks the queue — whichever is reached first. That is why E4 shows ≈1 s (≈30 frames) of slack at 30 fps.

Your turn in the repo

Prototype the real Phase 2 topology with data sinks before any C++ exists. From docs/ARCHITECTURE-SERVER-CLIENT.md, one capture feeds two profiles. Translate it to this lab (10-second window, then inspect sizes; adjust the timeout so timeout is what stops it):

timeout 10 gst-launch-1.0 -q videotestsrc is-live=true ! videoconvert \
  ! video/x-raw,format=I420,width=1920,height=1080,framerate=30/1 ! tee name=t \
  t. ! queue ! videoscale ! video/x-raw,width=1920,height=1080 \
    ! x264enc speed-preset=ultrafast tune=zerolatency key-int-max=30 ! filesink location=hd.264 \
  t. ! queue ! videoscale ! video/x-raw,width=1280,height=720 \
    ! x264enc speed-preset=ultrafast tune=zerolatency key-int-max=30 ! filesink location=sd.264
