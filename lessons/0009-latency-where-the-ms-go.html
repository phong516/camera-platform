Where the Milliseconds Go (and a Story About Stale Numbers)

Tune-in time is a number your platform will be judged on — so it needs a measurement, not a memory. This lesson builds the metric, takes it, and retracts an earlier number that didn't survive contact with the final binaries.

Mission tie-in: The architecture doc promises "100–300 ms settle". After this lesson you'll have your own reproducible tune-in metric and the first real numbers for all three server topologies you've built.

The metric: first frame, from client's PLAY to pixels arriving

labs/lab5-rtsp-client.cpp now stamps start_us just before set_state(PLAYING) and records the first new-sample delay. That single number contains everything the user experiences as "tune-in": RTSP connect (DESCRIBE/SETUP/PLAY), server media prepare, first RTP delivery, jitter buffer (none — latency=0), depay.

./lab5client rtsp://127.0.0.1:8554/hd 5
[client] ... samples=148 over 5.0s => 29.6 frames/s | first frame at 99 ms

What these numbers say

The bridge architecture is not the latency cost — it's the latency win. Pre-seeded appsrc media tunes in fastest (31 ms) because the media already has caps + a frame when the client's PLAY arrives. The plain videotestsrc media needs ~90–100 ms of its own startup before the first RTP packet leaves.

All topologies are comfortably inside the doc's 100–300 ms promise on loopback, TCP, with latency=0. Whatever the platform's real network adds, it adds the same to all three.

Retraction: the "~2 s viewer-join" from Lesson 6's debug run

During Lesson 6 development, an instrumented debug run showed two ~1 s waits inside gst_rtsp_media_prepare for appsrc media. That number went into notes and the first version of Lesson 6. It does not reproduce with the final binaries — re-measured today: 31 ms. The old figure most likely belonged to the debug build's instrumentation or a transient; the honest record is: observed once, never reproduced, retracted.

Two habits this incident should leave behind: (1) quote a number only with the binary you'll ship it in, and (2) when a claim matters to a promise (tune-in!), re-run the experiment before the review — even if it "was measured once".

What we did not measure (be honest about scope)

  • UDP vs TCP transport. All clients used protocols=tcp. UDP typically trims a little latency (no retransmit ordering) at the cost of loss artifacts — worth one run before the review.
  • Client-side decode. Clients count h264parse output, not decoded frames. On a real Qt viewer add avdec_h264 and the decode cost shows up in tune-in again.
  • Remote network path. Loopback only; no packet loss, no MTU games.
  • Snapshot latency under load. 33–38 ms (Lesson 7) was measured on an idle system.

Check yourself

1. Which server topology tuned in fastest, and why is that not a coincidence?

31 ms vs ~90–100 ms. The bridge's pre-seed isn't just cosmetic: it makes the media "warm" before negotiation finishes. The handshake is not the dominant term — server-side media readiness is.

2. The earlier ~2 s tune-in number from the debug run turned out to be wrong. What exactly is the lesson?

The bug was process, not physics: a number measured once under different conditions was carried as fact. Today's numbers reproduce across runs; the old one never did.

3. Your client counts h264parse output. What does your "first frame at X ms" NOT include?

The metric spans PLAY→depaid access units. Decode is downstream of the counter; on a Qt viewer, add the decoder and re-measure before promising UI-visible tune-in.

Read the primary source

rtspsrc — the latency, buffer-mode and drop-on-latency properties define the client's latency/loss trade-off. Then GstRTSPMedia again, reading for the prepare lifecycle you're now measuring.
