Valve: The Switch That Also Kills

Turning a profile off with valve — and the preroll trap that turns it into a whole-pipeline outage.

Mission tie-in: Phase 2 exposes --drop <name> to turn individual profiles off without stopping capture. valve is the switch — but used naively it has a lethal failure mode you need to design around.
Recap from Lesson 1

Every branch after a tee carries its own queue. Queues give each branch a private thread and ~1 second of slack, so one branch being slow no longer blocks the others.

Concept: the switch

valve is a passthrough element with one job: its drop property (a boolean, writable at any time) decides whether buffers and events continue downstream or are discarded.

t. ! queue ! valve name=sd_switch ! videoscale ! … ! x264enc ! appsink
                     ^
                     └─ runtime: sd_switch.drop = true  →  SD profile off

Its drop-mode property picks what “discarded” means — this choice is the trap:

drop-modeWhat the valve does when drop=true
drop-all (default)Drops all buffers and all events. Nothing at all flows.
forward-sticky-eventsDrops buffers, forwards caps/segment — but sends no replacement data.
transform-to-gapConverts dropped buffers into GAP events and forwards sticky events. Special, as you’ll see.

drop-mode can only be set while the element is in NULL/READY — i.e. before the pipeline starts. drop itself can flip any time. (valve docs)

Lab: the whole-pipeline outage

V1 drop one branch at startup — everything dies
timeout 5 gst-launch-1.0 videotestsrc is-live=true ! videoconvert \
  ! video/x-raw,width=1280,height=720,framerate=30/1 ! tee name=t \
  t. ! queue ! filesink location=a.raw \
  t. ! queue ! valve drop=true ! filesink location=b.raw
stat -c '%n %s B' a.raw b.raw

The pipeline claims success…

Pipeline is live and does not need PREROLL ...
Pipeline is PREROLLED ...
Setting pipeline to PLAYING ...

…and yet nothing anywhere produces data:

a.raw 0 B     # branch A has no valve at all!
b.raw 0 B

Why: the valve drops branch B's very first buffer (and its events). Branch B's sink therefore never receives what it needs to finish preroll — and no sink renders until the pipeline's PLAYING state is genuinely committed, which is gated on every sink completing preroll. One starved sink freezes the entire pipeline, queues and all. (Non-live sources show the same failure as a permanent Pipeline is PREROLLING ....)

This generalises: any branch whose sink never gets its first buffer — miswired, starving, dropped — freezes every other branch too. You met the queue-less version of this in Lesson 1; this is the same gate with a different trigger.

Mechanics, measured with state probes (labs/lab-preroll-states.cpp, labs/lab-stall-mechanism.cpp)

Where the pipeline parks. Live pipeline, valve closed at startup, default async sink: the pipeline really commits PAUSED (a live source skips the gate for that step — “Pipeline is live and does not need PREROLL”) and then parks forever at PAUSED → PLAYING; the starved sink sits at READY → PAUSED; upstream elements do commit PLAYING. Non-live: the pipeline never even reaches PAUSED — stuck READY → PLAYING. Either way “stuck at PREROLLING” is just the informal name for this condition.

How the freeze spreads. ~1 s of buffers flow, then: the stopped branch's sink (parked in PAUSED, not rendering) stops consuming → its queue fills to the default 1-second limit (~30 buffers) → the tee's sequential push into that branch blocks → the source's own thread freezes → every other branch starves, including ones with open valves. Reopening the valve later has nothing to forward: no buffers ever arrive again. (Single-branch pipelines, with no wedged sibling holding the source back, can be rescued by a reopen — the multi-branch case cannot.)

Bus during the stall: silent. No ERROR, no WARNING, nothing — the last messages are normal startup ones. Detect it yourself: after set_state(PLAYING), watch gst_element_get_state(pipeline, &s, &p, timeout); a timeout with the sink still at READY pinpoints the starved profile.

What actually rescues the others

Three candidate fixes; only some work, and the reasons matter:

V2 transform-to-gap — works until an encoder eats the gap
timeout 4 gst-launch-1.0 -q videotestsrc is-live=true ! videoconvert \
  ! video/x-raw,width=1280,height=720,framerate=30/1 ! tee name=t \
  t. ! queue ! filesink location=a.raw \
  t. ! queue ! valve drop=true drop-mode=transform-to-gap \
  ! videoscale ! video/x-raw,width=640,height=360 ! filesink location=b.raw
stat -c '%n %s B' a.raw b.raw
a.raw 120827904 B    # branch A flows! (≈121 MB in 4 s)
b.raw 0 B            # gap events carry no data — expected

GAP events count as “data received” for preroll, so the starved sink completes preroll and the pipeline plays. videoscale and capsfilter pass gaps through fine.

But insert an x264enc before the sink — as Phase 2 will — and it breaks again:

# same as above, but branch B: … valve drop-mode=transform-to-gap
#   ! x264enc speed-preset=ultrafast tune=zerolatency ! filesink location=b.264
a.264 0 B    # x264enc does NOT forward the gap → sink never prerolls → frozen
b.264 0 B
V3 async=false on the starved sink
timeout 4 gst-launch-1.0 -q videotestsrc is-live=true ! videoconvert \
  ! video/x-raw,width=1280,height=720,framerate=30/1 ! tee name=t \
  t. ! queue ! x264enc speed-preset=ultrafast tune=zerolatency ! filesink location=a.264 \
  t. ! queue ! valve drop=true ! fakesink async=false
stat -c '%n %s B' a.264
a.264 1041741 B    # branch A encodes normally (≈4 s of H.264)

async=false tells the sink “don’t hold up the pipeline for my preroll”. It worked for fakesink here and drops CPU back to single-branch levels:

Configuration (720p30 live, x264enc ultrafast+zerolatency)CPU
One branch only (baseline)92.3 %
Two branches open (drop=false)182.0 %
Branch B dropped, async=false sink94.6 %

Caveat: the trick is sink-specific. The same async=false on a filesink behind an encoder did not rescue the pipeline in our tests. Your real sink is an appsink — behaviour must be verified per sink type, never assumed.

Update — verified on an appsink later (labs/lab-async-appsink.cpp)

Closed at startup + async=false: the pipeline plays (the open sibling branch finished byte-identical to a reference run), and reopening the valve at t=2 s delivered samples 65 ms later at full rate. So for appsink, starting closed can work — set the flag at construction time.

Closed at startup + default async=true: permanent freeze in a multi-branch pipeline — reopening the valve later does not rescue it (0 B and 0 samples forever, even after the switch flips open; single-branch pipelines are rescue-able by a reopen — see the mechanics box above). If you keep valves closed at startup, the starved sink must be async=false, or don’t start closed at all.

The filesink+encoder failure stands; the flag remains sink-specific. This is why the design rule below says verify your exact sink before relying on any of this.

The design rule that avoids all of this

Default rule: never start a pipeline with a valve closed. Open every profile at startup, let the pipeline preroll, and only then apply drops — that is also what users expect from “turn SD off”: a running stream being stopped, not a dead server. Mid-run drops are safe: preroll is long finished, and each branch's queue absorbs the starvation for its neighbours (Lesson 1, E4).

Refined by the appsink update above: starting closed is safe only when the starved sink is async=false — verified per sink type, never assumed. With appsink that combination works (and reopens cleanly); with a default async=true sink it is a permanent, unrecoverable freeze. Otherwise, if a profile must be off from the very first frame, then don’t build its branch at all — attach/detach branches instead of starving them.

Check yourself

1. Why did both files stay at zero bytes in V1?

The dropped branch's sink never received its first buffer, so preroll never completed anywhere — including on branch A, which had no valve at all.

2. Which fix kept the encoding branch alive at startup?

Queues don't gate preroll, and leaky drops still deliver no first buffer. async=false (on fakesink) worked; deferring the drop until after preroll is the approach we'll recommend for Phase 2.

3. Why is a mid-run drop safe for the other branches?

The preroll gate only guards startup. Once playing, a starving branch just fills its queue while the others keep going (Lesson 1, E4: fast branch reached 39 frames while the slow branch managed 7).
