The Loop You Own

lab8's client is 82 lines of instrumentation: connect, count, report, quit. The line that looks wrong is g_main_loop_unref(mloop_local) — because mloop already “is” the main loop. Both facts are true; they are about different things: an address is not an owner.

Mission tie-in: this client is the instrument that measured source death and rebuild in Lesson 8. The loop it runs is the same kind of object your RtspProfileServer will run — so the ownership rule here is the rule that keeps the server's shutdown clean.

What the client actually does

One sentence

lab8client connects to an RTSP mount, counts depayed H.264 access units as they arrive, prints the count every 500 ms, and exits after N seconds or shortly after EOS. It does not decode, display, reconnect, or handle bus errors.

The whole media path is one launch string in labs/lab8-rtsp-client.cpp:

rtspsrc location=... latency=0 protocols=tcp ! rtph264depay ! h264parse
  ! appsink emit-signals=true sync=false name=sink
PieceJob
rtspsrc latency=0 protocols=tcpConnect over TCP, no jitter buffer — loopback lab numbers, not a network measurement.
rtph264depay ! h264parseRTP packets → H.264 access units. One new-sample = one counted “frame”.
appsink emit-signals=true sync=falseEmit new-sample from the streaming thread; deliver as soon as data arrives instead of waiting for the clock.
gst_bin_get_by_name(..., "sink")Find the sink (returns a full reference; the client unrefs it after connecting signals).
on_new_samplepull_sample → count++ → gst_sample_unref. Nothing else.
on_eosSet a flag, print the count, schedule a quit 200 ms later.
Main loopA 500 ms report, a quit at secs, and the EOS quit.

That is the entire program. It is a counter with a clock — deliberately too dumb to hide server behavior. A real run against the lab8 server shows exactly what it is for:

$ ./lab8client rtsp://127.0.0.1:8554/cam 4
[+  538ms] samples=0
[+ 1039ms] samples=4
[+ 1540ms] samples=19
[+ 2040ms] samples=34
[+ 2541ms] samples=49
[+ 3042ms] samples=64
[+ 3542ms] samples=79
[+ 3886ms] EOS received after 90 samples
[+ 4038ms] done: 90 samples total

15 samples per 500 ms = 30 fps; 90 samples = gen1's 90 buffers, exactly; EOS was delivered cleanly. The freeze-and-resume story in Lesson 8 was this same counter doing nothing for 2.5 s.

It needs the server (and the server owns appsrc)

Yes — lab8client is the probe for lab8-rtsp-recover.cpp; run the server first, then the client. There is no appsrc in the client at all. The client is a consumer: rtspsrc receives RTP and ends in an appsink.

Without a server it does not complain: it prints samples=0 until the deadline and exits, because it never polls the bus. That is another deliberate simplification of the probe.

The appsrc is the server's injection point, and it does not exist until a viewer connects. The factory launch string creates it on demand:

// lab8-rtsp-recover.cpp — media built when the first client connects
( appsrc name=vsrc is-live=true do-timestamp=true ! h264parse
  ! rtph264pay name=pay0 pt=96 config-interval=1 )

On media-configure, the server finds that element and stores it (gst_bin_get_by_name(..., "vsrc")). Its producer pipeline ends in a different appsink (psink); each sample is restamped and pushed into vsrc. So the whole system has two appsinks and one appsrc:

SERVER (lab8-rtsp-recover)                          CLIENT (lab8client)
videotestsrc → x264enc → appsink(psink)
                           │ new-sample
                           ▼
                 restamp + gst_app_src_push_buffer
                           │
                     appsrc(vsrc) → h264parse → rtph264pay → RTSP/TCP
                                                                   │
                                                                   ▼
                                                    rtspsrc → rtph264depay → h264parse
                                                      → appsink(sink) → count++

With no client connected, the media (and therefore appsrc) does not exist; the producer still runs and its samples are dropped. Measured:

$ ~/cam-recon/lab8            # no client
[+   1ms] serving rtsp://127.0.0.1:8554/cam
[+ 908ms] producer gen=1 started (90 buffers)
[+3990ms] producer gen=1 hit EOS after 90 samples
[+3991ms] no viewers connected, nothing to forward

One loop, two threads

main thread                                   streaming thread
───────────                                   ────────────────
g_main_loop_run(mloop)                        rtspsrc → depay → parse → appsink
  ├─ report() every 500 ms ── reads count ──┐
  ├─ quit_timeout() at secs                 │  on_new_sample(): count++
  └─ quit_after_eos() at EOS + 200 ms       │  on_eos(): flag + schedule quit
                                            └─ both signals are emitted here

The appsink signals run on the streaming thread — the appsink docs say so explicitly for new-sample and eos. The main loop is not what makes samples arrive; GStreamer's threads do that. The loop is where the client keeps time, reads the counter, and — importantly — decides to shut down from a safe thread.

Why schedule the EOS quit instead of calling g_main_loop_quit() directly in on_eos? quit is thread-safe, but the teardown after run returns (set_state(NULL), unref(pipeline)) is not something you want to do from inside a streaming-thread callback. Deferring to the main loop moves shutdown to the main thread.

Lab instrument, not production code

count is written by the streaming thread and read by the main loop with no mutex or atomic. On this machine an aligned guint read/write is benign in practice, but it is still a data race by the C memory model. In camera-platform, guard shared counters with a mutex or use g_atomic_int_*.

Why unref at all?

Because g_main_loop_new() returns an owned reference. The GLib docs are literal about it: the caller “takes ownership of the data, and is responsible for freeing it” (g_main_loop_new). g_main_loop_unref() drops that reference; at zero, “the loop and all associated memory are freed” (g_main_loop_unref).

g_main_loop_run() does not consume your reference. In fact, GLib's implementation takes its own temporary reference for the duration of the call — the source comment is “Hold a reference in case the loop is unreffed from a callback function” — and drops it before returning (gmain.c, g_main_loop_run). So the count goes: 1 (yours from new) → 2 during run → 1 when run returns. Your unref is still owed.

The proof is a tiny experiment, labs/lab-main-loop-refs.c, built with AddressSanitizer so a missed unref is visible:

# build
gcc -g -O0 -fsanitize=address,undefined labs/lab-main-loop-refs.c \
    -o ~/cam-recon/looprefs $(pkg-config --cflags --libs glib-2.0)

# create, run, unref — clean
$ ~/cam-recon/looprefs own
  [run]  returned; is_running=0 (object is still alive)
  [unref] refs we own=0 -> freed

# create, run, forget unref — LeakSanitizer names the line
$ ~/cam-recon/looprefs leak
Direct leak of 16 byte(s) in 1 object(s) allocated from:
    #2 ... in g_main_loop_new
    #3 ... in main labs/lab-main-loop-refs.c:35
SUMMARY: AddressSanitizer: 16 byte(s) leaked in 1 allocation(s).

16 bytes is the whole GMainLoop allocation (context pointer + running flag + refcount). The own run exits clean; the leak run exits with a leak report pointing at g_main_loop_new. At process exit the OS would reclaim it anyway — but the habit is what matters, and in a long-running server the loop is created and destroyed on the shutdown path, where leaks and use-after-free are real bugs.

Then why mloop_local and not mloop?

Because mloop is not a second reference. It is a second pointer to the same object:

mloop_local ─┐
             ├──▶  GMainLoop object   ref_count = 1
mloop ───────┘

Only g_main_loop_new() increased the count. Assigning mloop = mloop_local copies an address, nothing more. One reference → one g_main_loop_unref(). You can pass either pointer to unref; the decrement is identical. The reason the code unrefs the local is discipline: the variable that received the owned reference is the variable that releases it. The global exists only so the callbacks can reach the loop — C has no closures, and g_timeout_add/g_signal_connect pass a bare gpointer.

After g_main_loop_unref(mloop_local), both pointers dangle. That is safe here because the next lines never touch the loop again: the process prints the total, sets the pipeline to NULL, and exits. If you added one more g_timeout_add(..., mloop) after the unref, you would have a use-after-free.

Double-unref shows the difference between “unref” and “stop”:

$ ~/cam-recon/looprefs double
  [unref 1] refs we own=0 -> object freed here
  [unref 2] calling unref again on the freed pointer
GLib-CRITICAL: g_main_loop_unref: assertion 'g_atomic_int_get (&loop->ref_count) > 0' failed

g_main_loop_quit() stops the run; it does not free anything (quit docs). g_main_loop_unref() frees at zero; it does not stop a running loop. Two verbs, two jobs.

The rule

Count references, not pointers. new → you own 1. ref → +1. run → borrows (its own temporary ref), returns with your count unchanged. quit → state change, no ref. unref → −1, free at 0. Aliases add no references.

The context is a second object (the server version)

“Main loop” is also used loosely for two objects. Keep them apart:

ObjectWhat it isIn the client
GMainContextThe queue of event sources (timers, sockets)The global default context; the loop holds a reference to it
GMainLoopThe run/quit controller that iterates a contextmloop_local, one owned reference
GSourceOne timer or fd watch (the two g_timeout_add calls)Owned by the context; the lab never keeps their IDs

The server version makes the two-object ownership visible. In lab5-rtsp-server.cpp:

GMainContext *context = g_main_context_new();       // ref 1: yours
GMainLoop *loop = g_main_loop_new(context, FALSE);  // loop takes its own context ref
gst_rtsp_server_attach(server, context);            // server adds sources to context
g_main_loop_run(loop);

g_main_loop_unref(loop);       // drop the loop's ref (and its context ref)
g_main_context_unref(context); // drop YOUR context ref

Two objects, two refs you own. Unref only the loop and your context ref leaks; unref only the context and the loop's ref keeps it alive. (The loop constructor really does g_main_context_ref() — see gmain.c, g_main_loop_new.)

In lab8-rtsp-recover.cpp both calls pass NULL: gst_rtsp_server_attach(server, NULL) and g_main_loop_new(NULL, FALSE) share the global default context. That is why only the loop is unref'd there — nobody created a context to own.

Why running the loop matters for the server

gst_rtsp_server_attach() only adds the server's sources to a context. It does not run them. Until g_main_loop_run() iterates that context, the server accepts no connections. The loop is the app's heartbeat, not a GStreamer detail.

The trap next door: sources outlive the loop

The client never stores the IDs returned by g_timeout_add, so the report source stays attached to the default context after the loop is freed. quit_after_eos stays attached too in a run where the fixed deadline wins (our 4 s run: EOS at 3886 ms schedules a quit for 4086 ms, but the 4000 ms deadline fires first). That pending callback still holds the old mloop pointer.

Nothing dispatches that context again before exit(), so this lab is safe. In a process that keeps running — your server — it is exactly the use-after-free the GLib docs warn about. The recommended pattern is to store the source ID and “explicitly remove that source from the main context using g_source_remove() when the owning object is finalized” (The Main Event Loop — memory management of sources).

Two more rules fall out of the same doc: a GMainContext “can only be running in a single thread”, and event sources are associated with a context, not with a loop. One loop, one context, one thread that runs it — per application, not per profile.

What this means for camera-platform

  • One loop for the app. Application should own it; ProfileHost, ProfileBin and RtspProfileServer borrow it. Creating a loop per profile would mean multiple threads iterating the same default context.
  • Shutdown order: quit → run returns → stop/tear down pipelines and the RTSP server → remove your timer sources → unref the loop (and the private context, if you made one) last.
  • Qt integration is an open design question. Qt has its own event loop; do not block it and do not run a second GLib loop on the GUI thread. The options are a GSource integration or a dedicated GLib thread that marshals to Qt. Bring a choice to the review — it is the same “who owns the loop?” question at a larger scale.

Check yourself

1. What does g_main_loop_run() do to the one reference you own?

GLib holds a temporary reference while running and drops it before returning. Your reference from new is untouched — so one unref is still owed.

2. Why doesn't mloop = mloop_local create a second reference?

Assignment copies an address. Only g_main_loop_ref() (or new) changes the count; two names for one object still need exactly one unref.

3. What happens if you unref the loop twice?

The first unref takes the count to zero and frees; the second trips the ref_count > 0 assertion. Unref is refcount math, not a stop button.

Read the primary source

GLib — The Main Event Loop: read the whole page, then re-read “Memory management of sources”. That section is the source of the pending-source trap above. For the API contract, keep GMainLoop and GMainContext open beside it. For the client half, the appsink signals page states which thread emits new-sample and eos.
