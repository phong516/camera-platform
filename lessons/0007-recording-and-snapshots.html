Recording & Snapshots: The EOS Message That Never Comes

Two derived streams from one tee: an on-demand MP4 recorder, and a 35-millisecond JPEG snapshot. One of them taught us that EOS messages are a lie when other branches are alive.

Mission tie-in: Phase 3 asks for recording and snapshot endpoints on the same live stream as RTSP. Both are branches — the tee patterns from Lessons 3–4, one level up. Nothing new under the sun; two new traps in the details.

Concept: derived outputs are just more branches

producer (videotestsrc→x264) ─▶ tee ─┬─ queue ─▶ appsink        (RTSP bridge, always on)
                                      ├─ queue ─▶ h264parse ─▶ mp4mux ─▶ filesink   (recorder, on demand)
                                      └─ queue ─▶ valve ─▶ jpegenc ─▶ appsink      (snapshots, one frame)

The trap: waiting for the EOS bus message hangs forever

The natural stop-detection — gst_bus_timed_pop_filtered(bus, timeout, GST_MESSAGE_EOS) — timed out in every single run, even though the file finalized correctly. The investigation, in order:

  1. A bus watch logging every message for 6 s: not a single eos message. Ever.
  2. A pad probe on the filesink's sink pad: PROBE: EOS reached filesink0:sink — the EOS event arrives instantly.
  3. grep moov recdbg.mp4 immediately after: moov present — mp4mux had already finalized before forwarding the event.

Why no message: sinks don't put their EOS message on the bus for you to see directly — their parent GstBin consumes child EOS messages and only aggregates upward when all sinks in that bin have finished. Our pipeline has a second sink that never finishes: the always-on RTSP branch. So the pipeline-level EOS never fires. You can wait for it until the heat death of the universe.

The fix — detect finalize by event, not by message 
gst_pad_add_probe(gst_element_get_static_pad(filesink, "sink"),
                  GST_PAD_PROBE_TYPE_EVENT_DOWNSTREAM, on_branch_event, NULL, NULL);
/* callback: GST_EVENT_EOS arriving here means mp4mux already wrote the moov */

EOS arriving at the sink is the commit point: mp4mux finalizes its file during EOS handling, then forwards the event downstream. Probe fires = file complete. Keep the timeout fallback for a wedged branch, but with the probe it never triggers (1–2 ms).

Lab 2 — snapshots (labs/lab7-snapshot.cpp)

The snapshot branch exists from startup, gated by a start-closed valve — which is Lesson 4's resolved pattern again: valve drop=true + appsink async=false means no preroll wait, no permanent stall. On request: open valve, poll gst_app_sink_try_pull_sample(sink, 0) from the main loop, close valve when a frame lands.

Snapshot implementation rules

1. With drop=true + max-buffers=2 on the appsink, subscribe by polling try_pull_sample with a zero timeout from the main loop — never block a callback. If you ever wire snapshots to an HTTP worker thread, that thread cannot run a main-loop poll: give it its own mutex-protected "latest JPEG" slot that the main loop fills.

2. The frame you get is ≤ 1 frame period + encode time old relative to "now" — fine for security snapshots, wrong for measurement. Don't timestamp physics experiments with it.

Check yourself

1. Your recorder pushes EOS into the branch and waits 30 s on the bus for an EOS message. The file is already on disk, complete. Why no message?

The probe proved the EOS event reached the filesink in ~1 ms and moov was already written. The message is eaten by bin EOS aggregation; the always-on RTSP branch means the aggregate never completes.

2. What is the reliable "the recording file is complete" signal from inside the pipeline?

mp4mux finalizes during EOS handling and only then forwards the event. The event passing the sink pad probe is a happens-after guarantee that moov is on disk. The message may never come; the event always does.

3. A snapshot branch keeps a valve start-closed plus appsink async=false. What does that buy you?

Lesson 4's fix, reused: a starved branch would otherwise hold the whole pipeline in preroll. async=false makes that sink "ready anyway", the valve drops frames before the encoder, and the tee stays unblocked.

Read the primary source

mp4mux — read the faststart, faststart-file and reserved-moov-update-period properties with the crash experiment in mind. Then pad probes — you'll use them again for the recorder-confirm path in the server.

Your turn in the repo

  1. Recording service design: Recorder = the inverse of ProfileHost — attach/detach a branch from the source tee. Write it once your ProfileHost exists (they share the ghost-pad/mid-run-join crafts).
  2. Or snapshots first — they're smaller: one always-on branch, one valve, one JPEG pull. Wire it to the web API's snapshot endpoint when that lands.
  3. Decide and document the shutdown contract: on process exit, all active recorders get unlink + EOS + ≤2.5 s drain, then the pipeline goes NULL. Without that, every forced exit eats a recording.
When you bring a Recorder or Snapshot design, ask for the trap-audit: who owns the ghost pad ref, when is set_state allowed to run relative to the tee lock, is the probe callback safe on the streaming thread, and what happens if a second record is requested while one is draining.
