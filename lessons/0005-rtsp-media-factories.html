RTSP: Mount, Factory, Media

Your profile bins were the hard part. The server is four objects and ~60 lines — measured end to end: two mounts streaming at 29.7 fps each, viewers arriving and leaving cleanly.

Mission tie-in: This becomes server/RtspProfileServer: one port (8554), one mount per profile (/hd, /sd, …), shared factories so N viewers of the same profile cost one encoder. The launch pipelines here still contain their own videotestsrc; Lesson 6 replaces that source with your ProfileHost via appsrc — that is the bridge.

Concept: the three-object model

gst-rtsp-server is a library, not a plugin. You write a normal C program that fills three roles:

GstRTSPServer          owns the TCP port (service "8554"), accepts clients        signal: client-connected
   │
   └─ GstRTSPMountPoints     the URL → factory table            /hd → factory A, /sd → factory B
         │
         └─ GstRTSPMediaFactory     a pipeline TEMPLATE (launch string)
               │                     parsed on demand, per viewer session
               └─ GstRTSPMedia      the live media pipeline (one per session, shared among
                                    concurrent viewers of the same mount)     signals: prepared, unprepared

The factory is lazy by construction: nothing is encoded until a client asks for a mount. When a client DESCRIBEs /hd, the factory parses its launch string, builds the pipeline, attaches RTP payloaders, and starts it — on demand. That is exactly the "lazy profile" behavior your architecture doc wants, for free.

The launch string has rules

( videotestsrc is-live=true pattern=smpte ! videoscale !
  video/x-raw,width=1280,height=720,framerate=30/1 !
  x264enc speed-preset=ultrafast tune=zerolatency key-int-max=30 bitrate=2500 !
  rtph264pay name=pay0 pt=96 config-interval=1 )
  • The whole thing is wrapped in ( ... ) — it is one pipeline the factory builds and manages.
  • The payloader must be named pay0 (stream 0). A second stream would be pay1.
  • The source should be is-live=true — a live source returns frames immediately, so the first client gets video without waiting for a preroll that cannot happen.
  • config-interval=1 re-sends SPS/PPS every second, so a client that joins mid-stream can decode from the next keyframe. With real cameras you want this (and a sane key-int-max); without it, every new viewer waits up to a GOP for usable video.

1.28 API drift — two landmines we hit

1. gst_rtsp_server_create_main_loop() no longer exists. You now create the context yourself: GMainContext *ctx = g_main_context_new(); GMainLoop *loop = g_main_loop_new(ctx, FALSE); gst_rtsp_server_attach(server, ctx);

2. The factory signal is media-configure — not the media-configured you may half-remember from older examples. GObject signal names are not in headers, so check the GIR: grep 'glib:signal' /usr/share/gir-1.0/GstRtspServer-1.0.gir. That file is the ground truth for this exact install.

What the log just taught you about media lifetimes

ObservationEvidence
Shared means shared among concurrent viewers. Two clients on /hd → one media-configure, one media pipeline, one x264enc. The second viewer multiplexes onto the existing stream.1 signal, 2 clients
Media dies with the last viewer. unprepared fires when the client side is empty; a later client triggers a brand-new media-configure — we saw a fresh pipeline (bin2) built for the reconnect.new media per session
Nothing runs between sessions. No viewers, no pipeline, no encoder — you are not paying for idle profiles.prepared → unprepared → gone
These two signals are your viewer lifecycle

media-configure (viewer arrived — wire your stream in) and unprepared (viewers gone — unwire). Lesson 6 hangs the valve on exactly these edges: valve open on configure, closed on unprepared. The "shared media rebuilt per session" detail is why the wiring must be re-done every time, not once at startup.

Wrong mount, for completeness — the client fails fast, no hang:

details, rtsp-status-code=(uint)404, rtsp-status-reason=(string)"Not\ Found";
ERROR: pipeline doesn't want to preroll.
Measured aside: bitrate is a target, not a contract

Same 2500 kbps encoder setting: the ball test pattern (mostly static black) produced 157 kbps — x264 ABR undershoots when the scene compresses well. The smpte bars held 1219 kbps against a 1200 target. Your camera's real bitrate will move with the scene; budget for the ceiling, not the average.

Check yourself

1. Who builds the media pipeline for a mount?

Factories are lazy: nothing is built until a client requests the mount. That is why an unwatched profile costs zero CPU.

2. Two clients watch /hd on a shared factory. How many encoders run?

Measured: two concurrent clients produced exactly one media-configure and one set of frames. Shared = multiplexed onto the same encoder output.

3. All viewers leave, then one reconnects a minute later. What happens?

The media was destroyed with the last viewer; the reconnect got a new pipeline (bin2), not the old one. Shared only covers concurrent viewers.
