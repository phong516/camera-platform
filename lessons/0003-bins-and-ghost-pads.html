Bins & Ghost Pads: One Branch, One Box

Packaging a whole profile branch into one reusable element with a single pad — the exact shape of server/ProfileBin.

Mission tie-in: Phase 2 gives each profile its own queue ! valve ! videoscale ! capsfilter ! x264enc ! appsink chain. On paper that's N chains (N×6 elements) for N profiles. With a GstBin, each chain becomes one element with one sink pad — ProfileHost then manages N boxes instead of 6N parts.
Recap from Lessons 1–2

Every branch after the tee has its own queue (thread + ~1 s slack). valve.drop switches a branch off at runtime — but drop it only after preroll, or the starved sink freezes the whole pipeline.

Concept: the box and the proxy pad

A GstBin is a container that is itself a GstElement. You add elements to it, link them internally, and from the outside the bin participates in the pipeline like a single element: state changes, bus messages, clock selection and refcounting all delegate to its children.

The catch: a bin’s internal elements have their own pads. When the host pipeline links a tee to this branch, which pad does it link to? By default: none that the host can see — the bin would be a box with no handle. The handle is a ghost pad:

Definition

“GhostPads are used to build complex compound elements out of existing elements. They are used to expose internal element pads on the complex element.” — Ghostpads design doc

                    bin "sd"
        ┌──────────────────────────────────────────────┐
tee ────┤ sink(ghost) → queue ! valve ! videoscale ! … │
        └──────────────────────────────────────────────┘
           ^ host sees exactly this one pad

A ghost pad is a proxy: data landing on it is forwarded to the internal pad it targets (here: queue’s sink pad). The host links to it as if the bin really had that pad. Internals stay private — which is the point when we later swap the filesink for an appsink without touching host code.

The API moved — read old tutorials with care

Older tutorials (and some 1.x books) use gst_element_add_ghost_pad(bin, target, name). That helper is deprecated and gone from the 1.28 headers on this machine. The current way is two calls:

ghost = gst_ghost_pad_new("sink", target_pad);  // floating ref, refs the target
gst_element_add_pad(bin, ghost);                // add_pad consumes the floating ref

GstGhostPad reference · the design doc above explains the internal machinery (internal proxy pad, target swapping, activation) if you ever need it.

Lab: build the box, drive it at runtime

Full source: labs/lab3-profile-bin.cpp in this repo. It builds one profile bin (queue ! valve ! videoscale ! capsfilter ! x264enc ! filesink), attaches it to a live videotestsrc ! tee, and drops the branch at t=3 s:

cd /tmp/cam-recon
g++ -Wall -O2 -o lab3 /home/phong/camera-platform/labs/lab3-profile-bin.cpp \
    $(pkg-config --cflags --libs gstreamer-1.0)
./lab3
[t=3s] valve.drop = true        file=983326 B
[t=5s] (branch dropped)        file=983326 B
[t=6s] quitting                file=983326 B

At 2500 kbit/s you expect ≈313 KB/s of H.264, so ≈940 KB after 3 s — measured 983,326 B (encoder warming up, close enough). Then the branch is switched off and the file is frozen to the byte for the rest of the run: the valve discards everything after it, deterministically. No in-flight frames leaked into the file.

The three interesting lines (inside profile_bin_new)

GstPad *q_sink = gst_element_get_static_pad(queue, "sink");
GstPad *ghost  = gst_ghost_pad_new("sink", q_sink);
gst_object_unref(q_sink);              // ghost holds its own ref to the target
gst_element_add_pad(bin, ghost);       // consumes ghost's floating ref
gst_element_no_more_pads(bin);         // static bin: tell the core nothing else will appear

How the host attaches it (and why request pads)

GstPad *tee_pad = gst_element_request_pad_simple(tee, "src_%u");
GstPad *bin_pad = gst_element_get_static_pad(bin, "sink");   // the ghost
gst_pad_link(tee_pad, bin_pad);
gst_object_unref(tee_pad);   // you hold one ref; the tee keeps its own
gst_object_unref(bin_pad);

// later, from the host: flip the switch by name, inside the bin
GstElement *valve = gst_bin_get_by_name(GST_BIN(bin), "pvalve");
g_object_set(valve, "drop", TRUE, NULL);
gst_object_unref(valve);
Ownership in one table
CallRef you getWho releases it
gst_ghost_pad_newfloatingconsumed by gst_element_add_pad

Naming note: internal elements use short fixed names (pq, pvalve, …). Lookups via gst_bin_get_by_name are scoped to the bin, so sibling bins may reuse the same internal names — as this lab does for hd and sd in Lesson 4.

Check yourself

1. Why wrap the whole branch in a bin with a ghost sink pad?

Encapsulation is the point: ProfileHost manages N one-pad boxes, and swapping filesink → appsink later touches only the bin. The preroll gate from Lesson 2 is unaffected.

2. What does gst_ghost_pad_new hand back to you?

Floating ownership: adding it to the bin transfers it. The target pad is a separate matter — the ghost refs the target, so you unref your own reference to the target afterwards.

3. How does the host attach a bin to the tee?

Each branch needs its own request pad (src_%u); a pad can only have one peer, so reusing a linked pad fails. allow-not-linked just permits branches to be temporarily missing — it links nothing.

Read the primary source

Skim the GstGhostPad reference (2 minutes — mostly ownership annotations), and keep the design doc bookmarked for when ghost pad activation surprises you (it explains the internal proxy pad pair and how linking a pad to a targetless ghost pad auto-targets it — a trick you may want for dynamic attach/detach later).
